# Rubric: is this pull request ready to submit?

Every package is read as AI-assisted work. "Plan" means the posted plan
plus its deviation/deferral notes (live: `plan.md` including
`## Deviations`). "Disclosed" means stated in the plan's notes or the
PR description in plain words; a disclosed shortfall is a pass, a
silent one is a fail.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | Every file and hunk in the diff, read against the plan's scope, named files, and "not in scope" list. Check every hunk, not just the first; the description's claims about scope do not count as evidence here | Pass if every hunk is either the planned change, a test for it, or an artifact the repo's template/contributing guide requires for any change (changelog/whatsnew entry, i18n string, regenerated docs), or is named as a deviation in the plan or description. Fail if any hunk does work the plan does not name: an extra file or function rewritten, a new flag/config option/setting, a renaming or refactoring pass, a dependency bump, or anything the plan explicitly scopes out, even when the planned fix is also present and correct | required |
| plan-delivered | Each deliverable the plan commits to (the fix, each named file, docs or test it promises), read against the diff | Pass if every planned deliverable appears in the diff, or its absence is disclosed in the plan's deferral/deviation notes or in the description. Fail if a planned deliverable is missing from the diff without disclosure, or if the diff never implements the plan's actual fix (for example a dependency bump or formatting change in place of the planned code change) | required |
| description-faithful | Every factual claim in the PR title and description (what changed, "exactly as planned", "no changes beyond", "docs now say", "no functional changes outside X"), read against the diff | Pass if every claim in the description is true of the diff and the description mentions each substantive change the diff makes. Fail if the description claims something the diff does not contain, claims fidelity to the plan ("exactly as planned", "no other changes") while the diff does more or less, or omits a behavior change the diff makes | required |
| decisive-evidence | The test evidence (and before/after blocks in the description), read against the plan's test plan and the issue's repro | Pass if the evidence shows the plan's repro re-run with observable output (pasted output, exit code, error text, or a concrete UI step-by-step result) both before the fix (or the issue's captured failure) and after it, on the same input the issue fails on, and covers every failure mode or repro the plan's test plan names (a named one may be skipped only if the skip is disclosed). Fail if the evidence is prose only ("tested locally", "works now", "verified on my machine"), if it runs only a control or a path the fix does not change (single-file case when the bug is multi-file, GET when the bug is POST, a different header than the issue's), if the after is shown with no before, or if one of the plan's named repros is silently missing | required |
| repo-checks-run | The test evidence's suite/check results, read against the checks the plan's test plan and the repo's template/contributing guide name (live: `make test-unit`, `make test-integration`, `make lint`, `make typecheck`) | Pass if the repo's own test suite (and any checks the template names) is reported as a named command with its result (counts, "passes", or an honestly reported failure with its reason). Fail if no suite run is shown, or the evidence says only "tests pass" with no command named. A named suite command reporting pass counts even without full output | required |
| diff-clean | Every added or changed line in the diff, and the commit messages | Pass if every changed line serves the change: code, tests, and comments that explain the fix. Fail if the diff adds any debris: debug prints or logging left in (`eprintln!("DEBUG`, `print(`, `console.log`), commented-out code or earlier attempts, dead functions (including ones behind `allow(dead_code)` or named `_unused`), new TODO/FIXME notes, import reordering or restructuring, re-indentation or reformatting of lines the fix does not change, lines deleted and re-added identically, or hunks in files unrelated to the fix. Commit messages like "wip" or "misc cleanups while debugging" corroborate a fail but do not cause one alone | required |
| template-asks-met | The repo-facts "pull requests" line (live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), each stated ask read against the description and diff | Pass if the repo states no PR template or asks, or every unconditional ask is met: the issue link line it asks for ("closes #N", "fixes #N"), each section it names has real content (inline labels like "Problem:" count; exact headings do not matter), each checklist item is addressed, and every file entry it requires (changelog, whatsnew, docs) is actually in the diff, not just claimed. Conditional asks ("screenshots if appropriate", "for UI changes") pass when the condition does not apply. Fail if any unconditional ask is visibly ignored, or a required file entry is absent from the diff | required |
| ai-disclosure | The repo-facts "contribution policy" line (live: `docs/CONTRIBUTING.md` and any AI policy, plus the course rule that every PR discloses AI use in Notes for Reviewers), read against the description | Pass if the repo states no AI policy, or the description meets everything the policy requires: if it requires disclosing all AI usage, the description names the tool and the extent of the help; if it requires human-written text or a human in the loop, the description says so in the contributor's own words. Fail if a required disclosure is missing or incomplete (for example, no tool named where the policy requires it), or the repo bans AI-assisted contributions. In live mode, the course rule always applies: fail if Notes for Reviewers has no own-words AI-use disclosure | required |
| regression-test | The diff's test files, read against the issue's failing input | Pass if the diff adds or updates a test that exercises the issue's failing input on the changed path | preferred |
| title-clear | The PR title, read against the diff | Pass if the title names the behavior fixed specifically enough that a maintainer could tell what the diff does without opening it | preferred |

## Verdict rule

Accept (ready to submit) if every required check passes. Reject (hold)
if any required check fails or is graded unclear: a PR whose required
check cannot be confirmed from the package is not ready to submit.
Preferred checks never change the verdict. A check whose condition
says "pass if the repo states no X" (no template, no AI policy) passes
when the package shows no X; that is a pass, not an unclear. A
shortfall that the plan or description discloses is not a fail of
diff-within-plan, plan-delivered, or decisive-evidence; the same
shortfall left unstated is.
